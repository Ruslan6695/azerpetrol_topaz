# Подключение сторонних библиотек

## Правило 1. Сначала context7, потом код

Перед тем как написать первую строку кода с новой библиотекой — **и перед тем как менять код при обновлении мажорной версии** — обязательно получи актуальную документацию через MCP-сервер **context7**:

1. `resolve-library-id` — найти ID библиотеки.
2. `query-docs` — запросить документацию по нужной теме с этим ID.

Точные имена инструментов — вида `mcp__plugin_context7_context7__resolve-library-id` / `...__query-docs`; если они не в списке доступных, найди их через `ToolSearch` по запросу `context7`.

**Почему это правило существует:** проект на Expo SDK 54 / RN 0.81 / React 19 / New Architecture. API библиотек RN-экосистемы ломается между мажорами, а знание модели о них устаревает. Код, написанный по памяти, компилируется и падает в рантайме на устройстве — там, где ошибка стоит дороже всего.

Это касается любой сторонней библиотеки: и новой зависимости, и той, что уже в `package.json`, но с которой раньше не работали.

Если context7 недоступен или не знает библиотеку — переходи на `WebFetch` официальной документации **нужной мажорной версии** и явно скажи в отчёте, что context7 не сработал. Писать по памяти — не вариант.

Развёрнутый ресёрч с сохранением в `.library_docs/` — скилл `research-documentation-skill`.

## Правило 2. Ставим через `npx expo install`

```bash
npx expo install <package>     # ✅ подберёт версию, совместимую с SDK 54
yarn add <package>             # ❌ поставит latest, потенциально несовместимый
```

`yarn add` допустим только для чисто JS-пакетов, у которых нет соответствия в реестре Expo. Версии из блока `dependencies`, привязанные к SDK (`expo-*`, `react-native-*`), руками не правим — их двигает `expo install --fix`.

## Правило 3. Нативный модуль = пересборка dev-билда

Если библиотека содержит нативный код или требует записи в `plugins` в [app.config.ts](../../app.config.ts) — Metro-релоада недостаточно, нужен новый dev-билд (`eas build --profile development`). Это надо сказать явно, а не оставить человека выяснять на устройстве.

Проверь по документации:
- нужен ли entry в `plugins` и нужны ли permission-строки в `ios.infoPlist` / `android.permissions`;
- совместима ли библиотека с **New Architecture** (`newArchEnabled: true`) — это первый вопрос при выборе, а не последний;
- нет ли уже установленной библиотеки, закрывающей ту же задачу (в проекте уже есть reanimated, gesture-handler, svg, webview, gifted-charts, lottie, moment, immer, zustand).

## Правило 4. Библиотека прячется за обёрткой в `shared/`

Стороннюю библиотеку не вызывают напрямую из `widgets/`, `features/` и `entities/`. Для неё заводится обёртка в `shared/`, как это уже сделано: `QrCode` (qrcode-svg), `RangePicker` (calendar-range-picker), `ToastComponent` (toast-message), `CameraScanner` (expo-camera), `HtmlContent` (webview + render-html), `Skeleton`, `ImageCarousel` (reanimated-carousel), `GlassCard` (expo-blur).

Обёртка обязана привести библиотеку к правилам проекта: цвета из `ThemeStore.useCOLORS()`, размеры через `SIZES.PX`, текст через `Typography` (см. [styling.md](styling.md)). Именно поэтому чужой API не должен течь наружу — иначе тему и плотность придётся чинить в каждом месте вызова.

## Правило 5. Что фиксируем после подключения

- Новые экспорты обёртки — по [imports.md](imports.md) (невизуальное — в `src/shared/index.ts`).
- Изменения в `app.config.ts` — вместе с причиной.
- Отчёт о работе — в `plans/` (скилл `log-changes`), с указанием версии библиотеки и того, требуется ли пересборка dev-билда.
