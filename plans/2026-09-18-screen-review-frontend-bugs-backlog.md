# Ревью экранов — бэклог фронтенд-багов

Идём по экранам приложения по очереди (пользователь называет экран, разбираем
функционал). Решение (2026-09-18): бэкенд-баги чиним сразу по ходу разбора,
фронтенд-баги/недочёты — только записываем сюда, чтобы разобрать и
исправить отдельным заходом позже, не трогаем фронт походя.

Формат записи: экран → что не так → где в коде → почему не критично прямо
сейчас (если фикс отложен по причине, а не просто "потом").

## Известные бэкенд-баги, ОТЛОЖЕННЫЕ по просьбе пользователя (не фронтенд, но и не почищены сразу)

- **`profile/delete/confirm/` (шаг 2 удаления аккаунта — ввод кода подтверждения) сломан: HTTP 500 на каждый вызов.** Найдено 2026-09-20 не в ходе формального ревью экрана DeleteAccount, а при аудите «какие таблицы реально использует мобильное приложение» (обход `require_once` от всех точек входа `mobile_app/*`). `adapters/primary/mobile_app/profile/delete/confirm/index.php` требует `ports/primary/mobile/mobile_account_delete_confirm.php` — этого файла физически нет в репозитории (`require_once` несуществующего файла = PHP Fatal error). Шаг 1 (инициация удаления, звонок/смс — `mobile_account_delete_call.php`/`mobile_account_delete_sms.php`) существует и работает, `mobile_balance_account_delete.php` (удаление баланса при отказе от аккаунта) тоже есть — не хватает именно последнего звена, которое принимает код и завершает удаление. Пользователь попросил отложить фикс до отдельного захода — **не чинить самопроизвольно**, дождаться явного запроса. Когда будем чинить — сначала посмотреть `local-test/azsdemo` (там, по опыту проекта, такие «недостающие» мобильные эндпоинты обычно уже реализованы) как референс, не писать с нуля.

Подробности каждого фикса — в памяти Claude (`mobile-app-screen-review-project.md`) и в коммитах `azerpetrol-topaz-server` (сообщения коммитов подробные, с обоснованием и результатами живых проверок).

## Home

- **`ConvertBonusToBalance.tsx`** (`src/features/Home/ConvertBonusToBalance/ui/ConvertBonusToBalance.tsx:67`) —
  `if (bonusBalance <= 0) return null` пропускает `bonusBalance === undefined`
  (сравнение с `undefined` в JS всегда `false`, кнопка не скрывается).
  Раньше это реально стреляло из-за бага на бэке (`/home/` не отдавал
  `bonus_balance`, см. ниже) — сам баг на бэке уже исправлен
  (`azerpetrol-topaz-server`, коммит `0a12d78`, задеплоено и подтверждено
  вживую 2026-09-18), поэтому `undefined` в этом месте с высокой вероятностью
  больше не возникает. Не критично прямо сейчас, но защитную проверку стоит
  усилить на `if (!bonusBalance || bonusBalance <= 0) return null` — на
  случай, если подобный разрыв контракта повторится в другом месте.

## Fuel (главный экран заправки: метод → АЗС/колонка → топливо → литры)

- **`GetLocationOfAzs.tsx`** (`src/features/Fuel/GetLocationOfAzs/ui/GetLocationOfAzs.tsx:126-134`) —
  когда геолокация включена и запрос к `get_azs_geo/` успешно отработал,
  показывается тост «Геолокация включена. Азс будет определяться
  автоматически.» — но по факту ничего не подставляется:
  `FuelSelectAzsAndColumnWidget.handleSelectGeoAzs` — намеренная заглушка
  `(_azs) => {}` (см. комментарий там же), потому что `get_azs_geo/` отдаёт
  легаси-числовой id, несовместимый с id станций Топаз (строка). Сам факт
  отключённого автоподбора — уже задокументированное, осознанное
  ограничение (`plans/topaz-fuelling-integration-design.md`), но конкретно
  этот текст тоста никто не поправил — он лжёт пользователю, что станция
  подставится сама, хотя её всё равно нужно выбирать вручную на следующем
  шаге. Заодно сам запрос к `get_azs_geo/` продолжает уходить и тратить
  время геолокации впустую, раз результат всё равно отбрасывается.

## Contacts

- **`ContactsWidget.tsx`/`MapContacts.tsx`** (`src/widgets/ContactsWidget/ui/ContactsWidget.tsx`,
  `src/features/Contacts/MapContacts/ui/MapContacts.tsx`) — вероятная гонка
  вокруг `AsyncStorage`. `ContactsWidget` монтирует `checkIsContactInSystem(status)`
  в `useEffect` по `contactsPermission` — эта функция асинхронно читает ВСЮ
  телефонную книгу через `expo-contacts`, шлёт её на `get_contacts/` и только
  потом пишет результат в `AsyncStorage` (`EAsyncStoreKeys.CONTACTS`). Тем
  временем `<MapContacts>` рендерится в том же дереве и независимо читает
  тот же ключ `AsyncStorage` на своём собственном mount — никто ни на кого
  не ждёт. При медленной сети/большой книге контактов `MapContacts` может
  успеть прочитать `AsyncStorage` раньше, чем `checkIsContactInSystem`
  допишет туда результат — пользователь увидит пустой/устаревший список,
  пока не перемонтирует экран. Не проверено живьём (нужен реальный девайс
  с доступом к контактам и медленной сетью, не проверяется curl'ом) —
  зафиксировано как вероятная находка по чтению кода, не подтверждённый баг.
